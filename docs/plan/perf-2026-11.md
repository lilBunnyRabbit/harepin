# Performance pass, 2026-11 (t408)

0.59.0 (a5bdf29) against 0.63.1 (11dccc4). Measured 2026-11-17 on the owner's Windows box, nothing else running. Earlier rounds: `perf-audit-2026-11.md`, `perf-audit-2026-11b.md`, `sim-performance.md`.

## Short version

The frame is not lost in the game. In every driving case the JavaScript is 15-50% of the main thread and no app function is over 2% self time. The time goes to Blink doing document work once per frame, for three reasons that have nothing to do with what is drawn:

1. A mouse click inside any menu dialog leaves a caret on `<body>`, and Blink re-resolves it on every frame for the rest of the session. Phone tier, Mainland: 50 fps becomes 20.
2. The toast is anchor-positioned and stays in layout while invisible, so every frame's small HUD write pays a document-wide layout pass. Phone tier, Mainland: 64 fps becomes 91 without it.
3. The race clock sits under a `:has(:empty)` rule, so every clock tick recalculates the style of the whole document. A third of the main thread in every race.

1 and 2 got about twice as expensive between 0.59 and 0.63.1 because the page grew (5270 elements, menus kept in the DOM). 3 is the same in both. None of the nine suspects is a top cause; see [Suspects](#suspects).

## How it was measured

- `git archive` of each commit, `vite build` (production). The AI race needs `?airace`, which only a `--mode review` build has, so that case runs review builds of both commits. Traces and profiles run `--minify false` builds, for function names.
- `vite preview`, headless Chrome through Playwright on the real GPU (`--use-angle=d3d11`), service worker blocked, network to localhost only.
- Desktop: 1280x720, DPR 1, no throttle. Phone tier: 844x390, DPR 3, touch (so `Quality.mobile`), CPU throttle 4x. The throttle slows the main thread only: the GPU and the workers run at full speed, so a phone's GPU cost is not in these numbers.
- The display runs at 144 Hz: a frame gap of 6.9 ms is vsync, not the cost.
- Columns: **gap** is the time between animation frames; **work** is CPU time inside animation-frame callbacks; **long** is long tasks over 50 ms (count / longest); **main** is CDP `Performance.getMetrics` per second of wall time: all tasks (script / style recalc / layout); **heap** is the highest `usedJSHeapSize` sampled; **draws** is WebGL draw calls per drawn frame x drawn frames per second, by wrapping the WebGL2 draw calls (multi-draw counted once); **GL** is the WebGL contexts the page created since boot.
- Mainland roam: seed 1, gas held for 30 s, the car put back on the road when it stops. AI race: island seed 1, `?airace=circuit&aidrive&aicars=7`, 30 s from the moment the pack moves. Menus: 10 s idle.
- Run to run, a driving case moves by about 15% in fps (the car does not take the same path twice). Menu rows repeat within 1%.
- Scripts in `.t408/` (untracked): `measure.mjs` (cases, trace, CPU profile), `analyze.mjs` (self time per trace event and per function), `layout.mjs` (what invalidates style and layout, with stacks), `callers.mjs`, `parents.mjs`.

## Ranked causes

### 1. A click in a dialog leaves a caret Blink resolves every frame

- Chrome's own stylesheet gives `<dialog>` `user-select: text`. `Pause.svelte` and `MapOverlay.svelte` set it back to `none`; `menu/ui/Dialog.svelte` does not. A mouse press on a button in a `.ui-dialog` (the Updated card's Got it, any modal's buttons) starts a selection in the button's text.
- The dialog then leaves the DOM and the caret moves to `<body>`, child offset 58. `getSelection()` reports `Caret` on `BODY`.
- From then on, each frame that lays anything out runs `LocalFrameView::updateStyleAndLayoutIfNeededRecursive > VisibleUnits::canonicalPosition > mostBackwardCaretPosition`, which walks back through the document looking for a place a caret could sit. 75 of 76 frames in the trace, 23 ms each at 4x.
- 0.59.0 has the same bug at a quarter of the price: about 9 ms a frame at 4x against 36 in 0.63.1. The walk is over the document, and 0.63.1's has 5270 elements, most of them menu pages that are not displayed.
- Evidence: the same run with the card dismissed by a real click gives 18.3 fps, by `button.click()` from script 67.7 fps (6 s each, back to back). `getSelection().removeAllRanges()` before the sample gives 58.9 fps.
- Who it hits: anyone with a mouse, for the whole session, after one click in a dialog. A touch tap does not start a selection, so a phone is likely spared; not verified on a real phone.

Fix options:

| Option | Gain | Cost |
|---|---|---|
| A. `user-select: none` on `.ui-dialog`, as the other two dialogs have. Text fields keep their own `user-select: text` | all of it: phone tier 20 to 50 fps, desktop main thread 834 to 379 ms/s | none seen |
| B. Also drop any selection when the menu closes | covers a caret left in a text field or a build code that is then hidden | one line, only worth it if a test shows the case is real |

### 2. The invisible toast forces a document-wide layout every frame

- `#toast` is positioned with CSS anchor positioning (`position-anchor: --top-centre`, `anchor()`, `anchor-size()` in `hud/overlays.css`). Idle, it is `opacity: 0` but still laid out.
- Each frame the HUD writes the rev bar's width (`#rpm-fill`, `hud.ts`) and, a quarter of the frames, the speed text. Either makes Blink lay out; the anchored toast is then invalidated too (`Anchor positioning DIV id='toast'`, 223 of 224 layouts), and the layout is of the whole document (`partialLayout: false`, 4-7 dirty of 316 objects).
- Cost: 8.2 ms a frame at 4x in 0.63.1 (413 ms/s), 3.9 ms in 0.59.0 (313 ms/s).
- Evidence, 6 s samples back to back with the rule changed from the page: as shipped 64.3 fps, layout 395 ms/s; toast without its anchor 91.4 fps, layout 71 ms/s; toast `display: none` 101.7 fps, layout 66 ms/s. Pinning the rev bar's width instead changes nothing (50.5 fps, layout 435 ms/s): the bar is the trigger, the toast is the cost.

Fix options:

| Option | Gain | Cost |
|---|---|---|
| A. Take the toast out of layout while it shows nothing (`hidden`, set back when its fade ends) | phone tier about +40% fps on every drive; layout 395 to about 70 ms/s | the fade-out needs the element until it ends |
| B. Position the toast without anchors | the same | the toast no longer follows the card above it; layout rules per HUD form by hand |
| C. Rev bar by `transform: scaleX`, so it never invalidates layout | removes the trigger on most frames, not on speed changes | the bar's round end stretches: a look change |

### 3. Every race clock tick recalculates the whole document's style

- `Modes.write_status` (`modes/modes.ts`) writes the clock into `#mode-status-clock` every frame, through `set_text`, which already avoids the node swap.
- `hud/run-card.css:90` and `hud/phone.css:280` test `#mode-status:has(#mode-status-clock:empty)`. A text change under a `:has(:empty)` subject invalidates `#mode-status`, and `body:has(#mode-status:not([hidden]))` (six rules in `phone.css` and `run-card.css`) carries it to `body`: `UpdateLayoutTree` over 321 elements on 110 of 111 frames.
- Cost: 345 ms/s at 4x (about 11 ms a frame at 30 fps), 255 ms/s on desktop at 1x (1.8 ms a frame). Same in 0.59.0 and 0.63.1. It is in every mode with a running clock.

Fix options:

| Option | Gain | Cost |
|---|---|---|
| A. `write_status` sets an attribute on `#mode-status` when the clock goes empty or not, and the two rules read it | style recalc 320 to about 10 ms/s in races; phone tier race about +40% fps | none: same look |
| B. Write the clock at 10 Hz | a tenth of the recalcs | the clock steps |

### 4. A map load spends a third of the main thread placing event markers

- `event_markers > parking / gymkhana > park_site / gym_site > find_site > site_score > to_local` on the main thread at boot: 1.3 s of a 4.1 s load at 4x. 920 ms of it is the deterministic `sin` / `cos` (`rem_pio2`, `k_sin`, `k_cos`) inside `to_local` (`modes/gymkhana.ts:90`): `site_score` calls it for every solid on the map, for every candidate site, and each call takes that site's sine and cosine again.
- Fix: take the sine and cosine once per candidate site. Same output. Expected: about 0.9 s off a 4x load (3.8 to about 2.9 s), a quarter of a second on desktop. Further: run the search in the world worker, which is an architecture call.

### 5. The Garage keeps the whole frame loop running

- With the Garage open the loop never sleeps (`skips` excludes `garage.is_open`, `main.ts`), so `frame()` runs at the display rate with the sim held: 425 ms/s of script at 4x against 137 on Home.
- `modal_open()` (`hud/input.ts:181`) is `document.querySelector("dialog:modal")` over 5270 elements, each frame: 128 ms/s at 4x, 10.5% of the main thread.
- Since 8fd49c8 the world also redraws behind the Garage at 10 Hz: 54 calls x 9.5 a second on phone tier. That part is cheap.
- Fix: a `dialog` open flag kept by the dialogs instead of the query; sleep the loop under the Garage as under Home, waking on input. Expected: Garage main thread 586 to about 350 ms/s at 4x.

### 6. The car picker hitches while its stills draw

- Ten stills, one a frame, each builds a car model, draws it on a renderer of its own and encodes a WebP. The renderer is new for each batch, so its shaders compile again (`getProgramInfoLog`, `shaderSource`).
- Phone tier: 12-18 long tasks over 4 s, longest 143-186 ms, 1.1-1.6 s in all; the frame gap peaks at 271 ms. Desktop: one 56 ms gap.
- Fix options: keep the stills' renderer alive for the session (one context, shaders compiled once); draw stills on the showroom stage's renderer; ship the stock cars' stills as images. Expected: long tasks roughly halved by the first.

### 7. Smaller

- **three.js program re-keying in a race:** `getParameters` + `getProgram` + `getProgramCacheKey` 40 ms/s at 4x. A material shared by meshes that differ in instancing or vertex colours re-keys on every flip, as the shadow casters did (round 1, finding 2). Which material was not traced.
- **Mainland on desktop is draw-bound, in both versions:** 159 calls and 586k triangles a frame give 98 fps on a 144 Hz display with the main thread 30% busy. Not a regression.
- **Memory:** the heap peak is 20-40 MB higher in the menus (59 to 99 MB on phone-tier Home), and boot now creates 4-5 WebGL contexts where 0.59.0 made one (the Title stage and the still renderers). The contexts are given back; none draws per frame.
- **Layout costs twice as much per pass in 0.63.1** (8.2 against 3.9 ms at 4x) for the same 4-7 dirty objects. Cause 2's fix hides it; why the pass itself grew was not traced.

## Suspects

| Suspect | Verdict | Evidence |
|---|---|---|
| Two WebGL scenes (showroom stage, world behind the Garage) | Cleared as a frame cost | The stage draws on demand: 0 draw calls a frame idle. The world behind draws at 10 Hz, 54 calls on phone tier. What costs is the loop not sleeping (cause 5) |
| `backdrop-filter` over the canvas | Cleared for play and the new pages | Two rules are left: `.settings[data-view="page"]` (pages not yet rebuilt) and `.touch-buttons button`. No displayed element had one while roaming, in a race, on Title, Home, Garage or the picker (computed-style sweep). GPU cost of the two is not visible on this box |
| Realistic minimap blit | Cleared | `drawImage` 0.5% self time; hiding the canvas does not move fps |
| AI awareness at 360 Hz | Cleared | It runs at 20 Hz (`AWARE_STEPS`, `ai/field.ts`). All AI driving is about 45 ms/s at 4x with 7 cars |
| Route-lead updates | Cleared | Not in the top 40 self-time functions of the race |
| CarStill renders | Confirmed, as a hitch on open only | Cause 6. Stills are cached; nothing per frame |
| Streaming chunk work | Cleared | Clean Mainland roam: 0-3 long tasks in 30 s, no streaming function in the top 32 |
| Svelte re-renders per frame | Cleared | No Svelte runtime function in the top 32 (roam) or top 40 (race) |
| Neon | Cleared | Race draw calls and triangles equal 0.59.0, which had none: 142 calls, 182k |
